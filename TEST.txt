CS121 Assignment 3 - Milestone 3 Test Queries
==============================================

20 queries used to evaluate ranking quality (effectiveness) and response
time (efficiency). Queries 1-10 performed well; queries 11-20 performed
poorly on one or both criteria.

Parts A and B record the BASELINE results (the Milestone 2 engine) and
what went wrong. Part C describes each change we made to fix the poor
queries and the measured before/after results.

Baseline setup: index built from DEV (55,393 documents, 1,066,436 unique terms).
Each query was run 3 times; the time shown is the median, measured
inside SearchEngine.search() (index already loaded). Top 10 results
were inspected for each query.

Every query finished well under 300 ms (slowest: 74 ms), so "poor
efficiency" below means slow relative to the other queries.

---------------------------------------------------------------
ROOT CAUSES FOUND (BASELINE)
---------------------------------------------------------------
- Duplicate documents: 1,601 URLs are indexed twice, so the same page
  takes two result slots (queries 1, 4, 8, 9, 11, 12, 13, 14, 17, 19).
- No document length normalization: long listing/bibliography pages
  win (11, 12, 14, 17, 19).
- Stop words / very common terms: huge postings lists are fully parsed
  even though they barely affect the score (9, 14, 15).
- Strict AND with no fallback for rare or missing terms (16, 17).
- Low-idf terms give no ranking signal (15, 18).
- Flat important-tag bonus doesn't separate <title> from <b> (13, 18).
- No phrase/proximity scoring (12, 19).
- Tokenizer drops symbols and splits hyphens (10, 20).


===============================================================
PART C - IMPROVEMENTS AND THEIR EFFECT
===============================================================

---------------------------------------------------------------
Improvement 1: Exact and near-duplicate detection (indexer.py)
---------------------------------------------------------------
Problem it targets: duplicate pages taking two result slots (queries
1, 4, 8, 9, 11, 12, 13, 14, 17, 19) and wasted work on postings for copies.

What we did. While indexing, each page goes through three checks before
it gets a doc id; a page that fails any of them is skipped and logged to
index_data/duplicates.txt:
  1. Same URL (after removing the #fragment) already indexed -> skip.
  2. Exact duplicate: MD5 checksum of the page's token sequence. If the
     checksum was already seen, skip. This catches the same page served
     under two URLs, e.g. /faculty/ vs /faculty/index.php, or
     view_news?id=1187 vs view_news.php?id=1187.
  3. Near duplicate: a 64-bit SimHash fingerprint of the page (only for
     pages with >= 50 tokens, where SimHash is reliable). Each word is
     hashed to 64 bits and each distinct word votes +/- once on every
     bit (not once per occurrence; see "Side effect found and fixed"
     below); the fingerprint keeps the bits with positive votes. If a
     kept page's fingerprint differs in <= 3 of 64 bits, the new page is
     a near duplicate and is skipped.
     This catches pages that differ only in a date, counter or ad, such
     as successive versions of the same wiki page.

The technique is general: it doesn't depend on any particular query,
site or URL pattern.

Results (baseline -> with duplicate detection):
  Pages skipped: 1,601 repeated URLs, 3,214 exact duplicates and
  9,088 near duplicates. The index went from 55,393 to 41,490
  documents.

  Query                              matches        time (ms)   dup URLs in top 10
  1  cristina lopes                     84 ->    60   0.3 ->  0.2    3 -> 0
  4  informatics                     4,598 -> 3,121   3.8 ->  2.9    1 -> 0
  8  hackathon                         238 ->   137   0.2 ->  0.1    1 -> 0
  9  master of software engineering  1,749 ->   936  26.4 -> 16.9    2 -> 0
  11 machine learning                4,419 -> 2,377   9.2 ->  4.8    3 -> 0
  12 data science                    5,045 -> 2,699  14.9 ->  8.5    2 -> 0
  13 graduate admissions             2,073 -> 1,215   4.4 ->  2.6    2 -> 0
  14 how to apply to the university  1,940 -> 1,409  74.2 -> 45.9    4 -> 0
     of california irvine
  17 cristina lopes software ...      21 ->    14  28.7 -> 18.3    1 -> 0
  18 ics                            18,691 -> 10,478  14.9 ->  8.7    0 -> 0

  - No query has a repeated page in its top 10 any more (there were 20
    repeated slots across the 20 queries).
  - Queries are 1.3-2x faster because postings lists are shorter
    (slowest query, #14: 74 ms -> 46 ms).
  - Ranking improved where duplicates were the main problem:
    "cristina lopes" now shows 10 different pages about her (profile,
    news archives, award and grant news) instead of 3 pages twice each;
    "machine learning" no longer spends 4 of its top 10 slots on two
    copies each of two blog listing pages.
  - Duplicate detection doesn't fix the ranking problems that come
    from long listing pages (11, 12, 14, 19); those are next.

Side effect found and fixed:
  The first version weighted each word's SimHash vote by its term
  frequency. Because stop words are kept in the index, "the", "of",
  "and" dominated the votes, so long unrelated English pages got
  almost the same fingerprint. It removed 13,536 pages as near
  duplicates; in a random sample of 300 of those pairs, 43 shared less
  than half of their words (Jaccard similarity < 0.5). Real pages were
  lost: the ICS graduate admissions page was dropped as a "duplicate" of
  the graduate degrees page, and the 2009/2010 news archives were
  dropped, so "cristina lopes" fell to 49 matches.
  Fix: each distinct word votes once (binary weights). Near-duplicate
  removals fell from 13,536 to 9,088. In a new random sample of 300
  flagged pairs, 0 have Jaccard < 0.5 and the median Jaccard is 0.96.
  The admissions page and both news archives are back in the index
  ("cristina lopes": 49 -> 60 matches, archives at #2 and #3).

How ranking was measured for Improvements 2-4
---------------------------------------------------------------
For each query (except "the") we wrote down which pages a user would
actually want, e.g. Cristina Lopes's faculty profile for "cristina
lopes", the MSWE program pages for "master of software engineering",
cs.uci.edu or the CS department faculty page for "computer science".
We then recorded the rank of the first such page in the top 10 and
averaged 1/rank over the queries (mean reciprocal rank, MRR; 1.0 =
every query has a good page at #1, 0 = none in the top 10).
Index for all numbers below: the de-duplicated index (41,490 docs).

---------------------------------------------------------------
Improvement 2: BM25 ranking with page-length normalization (search.py)
---------------------------------------------------------------
Problem it targets: long listing / bibliography / archive pages won
because the old tf-idf score grew with raw term counts and was never
normalized by page length (queries 11, 12, 14, 17, 19, 20).

What we did. Replaced the score with BM25:
    score(d) = sum over query terms t of
               idf(t) * tf' * (k1 + 1) / (tf' + k1 * (1 - b + b * len(d)/avg_len))
    idf(t)   = log(1 + (N - df + 0.5) / (df + 0.5))
  - Extra occurrences of a word add less and less (saturation, k1=1.2),
    so a page that repeats "machine learning" 80 times no longer beats a
    page that is about machine learning.
  - Scores are divided by how long the page is relative to the average
    page (b=0.75), using page lengths already stored in docs.txt.
  - Important-tag text is folded into the term frequency: an occurrence
    in title/h1-h3/b/strong counts as 1 + 2 = 3 occurrences
    (tf' = tf + 2 * important_tf), instead of the old flat +2 bonus.
We used the standard BM25 values (k1=1.2, b=0.75). We also tried
b = 0.3 / 0.5 and important weights 1 / 4; b=0.75 with weight 2 was
best or tied, so we kept the textbook defaults rather than tuning to
our queries.

Results (old tf-idf -> BM25), position of the first good page:
  12 data science                    not in top 10 -> #1 (B.S. in Data Science)
  19 computer science                #6 -> #1 (CS department faculty page;
                                     cs.uci.edu home page is now #5)
  20 c++ programming                 not in top 10 -> #1 (ICS 45C C++ course)
  13 graduate admissions             #7 -> #3 (Informatics graduate
                                     application process is #4)
  3  donald bren school              #3 -> #1 (Bren Hall page)
  17 cristina lopes ... (long query) #4 -> #2 (her ICS faculty profile)
  11 machine learning                top 5 are now CML machine learning

                                     blog category listings and long
                                     publication lists
  Overall MRR@10: 0.52 -> 0.71 (with Improvements 3 and 4).

Side effects we observed (short pages now favored slightly too much):
  - "eppstein": #1 is still his home page, but two .git log files from
    his PADS project are #2-3 (short text files full of his name).
  - "cristina lopes": a student's home page that lists her as advisor is

  - "richard pattis": his home page dropped from #1 to #4 (#2 is his
    faculty profile).
  These are short pages where the query word is a large part of the
  text. The next planned change (weighting <title> separately and adding
  URL words) addresses them.

---------------------------------------------------------------
Improvement 3: Ignore very common words when the query has specific ones
---------------------------------------------------------------
Problem it targets: slow queries containing stop words (9, 14, 15).
The index keeps every word (no stop-word removal, as required), so
"of" (in 63% of pages), "the" (54%), "and", "to", "a", "in" and "for"
have very long postings lists. The old search read and parsed each of
them fully, even though they add almost nothing to the score.

What we did (all in search.py, the index is unchanged):
  - Before loading any postings we read only each term's document
    frequency, which is stored at the start of its line in index.txt
    (a few bytes, instead of parsing the whole list).
  - A term that appears in more than 35% of all pages is treated as a
    stop word, but only when the query also contains a more specific
    term. Those terms are not loaded, required or scored. The 35%
    cut-off is a gap in the data: the next most common words, such as
    "comput" (32%) and "project" (27%), are content words.
  - A query made only of common words ("the", "the of and")
    still uses all of its words, so it always gets results
    (e.g. "the of and": 17,023 matches).
  - Postings are parsed in one pass with built-in functions
    (str.split + map(int)) instead of a Python loop per posting, AND
    intersection starts from the shortest list, and the top k results
    are selected with heapq.nlargest instead of sorting every match.

Results (time per query):
  14 how to apply to the university of california irvine  45.9 -> 15.6 ms
  9  master of software engineering                       16.9 ->  6.5 ms
  15 the                                                  24.3 -> 21.6 ms
  The slowest of our 20 queries is now 21.6 ms ("the"), down from
  74.2 ms at the start. Ranking for "master of software engineering"
  also improved: mswe.ics.uci.edu is now #1.
  Query 14 is now fast but still ranks poorly (news pages, no
  admissions page); it needs the title/URL weighting planned next.

---------------------------------------------------------------
Improvement 4: Spelling correction and partial-match fallback
---------------------------------------------------------------
Problem it targets: queries that returned almost nothing because every
term had to be present (16 "machine lerning", 17 long query).

What we did (search.py):
  1. Run the normal "every term must match" search.
  2. If it returns fewer than k pages, look for typos: for each query
     word with at least 4 letters that appears in 5 or fewer pages, try
     every word one edit away (delete, swap, replace or insert one
     character), stem it, and look up its document frequency. If one
     is at least 20 times more common, use it instead and tell the user
     ("showing results for: ..."). Only rare words are touched, so
     normal names and terms are never "corrected".
  3. If there are still fewer than k pages, also include pages that
     contain only some of the terms. Results are ordered first by how
     many query terms they contain, then by BM25 score, so pages with
     every term always come first. The user sees a note that partial
     matches are included.

Results:
  16 machine lerning   1 match (a word list file) -> corrected to
                       "machine learning": 2,377 matches, CML machine
                       learning pages at the top, 7.6 ms.
  Other examples: "eppstien" -> "eppstein" (his home page #1);
  "cristina lopes zzqxqvv" -> no page has all 3 words, so the partial
  match fallback returns her pages instead of 0 results.
  17 (long Lopes query) has 14 full matches, so the fallback isn't
  needed; it improved through BM25 (Improvement 2).
